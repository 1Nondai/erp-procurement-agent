# 采购订单操作规范（下单 / 改单）

## 一、下单前必过的 5 道校验

1. **物料已确认**：`orderDetail[].partId` 必须是 `part_query` 查到的真实零件 ID，
   不能是零件名称或型号字符串。名称 → ID 的映射必须先查后填。
2. **数量与单价**：`quantity` 为 ≥1 的整数；`unitPrice` 为正值。
   单价优先取最近一次有效报价，取不到就问人，**不要用历史均值替代**。
3. **金额一致性**：传 `totalAmount` 时必须等于 `Σ(quantity × unitPrice)`；
   拿不准就**不传**，让后端按明细自动计算——算出不一致的总额比不传更糟。
4. **交期合理性**：`expectedDeliveryDate` 用 `yyyy-MM-dd`，且不早于今天；
   与供应商承诺交期不一致时，以供应商书面承诺为准并在 `remark` 里注明差异。
5. **供应商匹配**：物料与供应商的供货关系必须成立（`part_query` 的返回里带供应商信息）。
   同物料换供应商属于**改供应商**，需要重新确认单价与交期，不能只改 ID。

## 二、改单的最小变更原则

- 只传要改的字段，**不要整单回传**：整单回传会把并发修改的其他字段覆盖掉。
- 改状态必须先核对流转合法性（见下表），非法流转后端会拒绝：
  | 当前状态 | 允许流转到 | 说明 |
  |---|---|---|
  | 1 待审核 | 2 已审核、5 已取消 | 未审批可直接取消 |
  | 2 已审核 | 3 采购中、5 已取消 | 已审核后取消要记录原因 |
  | 3 采购中 | 4 已入库 | 采购中不可直接取消，需走退货流程 |
  | 4 已入库 | — | 终态，只能开退货单 |
  | 5 已取消 | — | 终态 |
- 已入库订单的金额/数量不可修改；确需变更走退货 + 重新下单两条记录。

## 三、审批前的自检（提交给人工审批之前）

- 用一句话复述**要做什么**：物料 / 数量 / 单价 / 总额 / 供应商 / 交期；
- 明确标出**与上次操作不同的地方**（改单场景），让审批人一眼看出变更点；
- 数据来源写清楚（哪个工具、哪次查询），不要把推测写成事实。

## 四、重复提交的自我保护

- 同一笔业务请求重复提交时，MCP 层幂等会返回首次结果并带 `idempotent_replay=true`；
  看到该标记要**如实告诉用户"这单没有重复下单，返回的是上一次的结果"**，不要当成新单汇报。
- 若返回 "该请求正在处理中"，说明有并发同指纹请求在执行：提示用户稍后查询订单状态，
  **不要立刻重试**。

## 五、失败处理

| 情况 | 处理方式 |
|---|---|
| 后端返回 4xx（参数/状态非法） | 读错误信息，修正字段后重试 **最多 1 次**，仍失败则如实汇报 |
| 后端返回 5xx / 超时 | 不要盲目重试：先 `order_search_details` 查该单是否已落地，再决定 |
| 关键字段拿不到 | 调 `request_order_info` 暂停等人补，**绝不编造** partId / 单价 / 供应商 |
| 审批被拒绝 | 停止执行，回复"已取消本次操作"，不要换个措辞再试一次 |
