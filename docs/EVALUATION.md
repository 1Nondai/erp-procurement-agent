# 评测体系设计（Evaluation）

> 一套评测的价值不在"分数好看"，而在**改完之后能不能立刻知道有没有变差**。
> 本文说明本项目为什么这么分层、用例为什么这么写、以及哪一层还没做。

## 1. 为什么分层

Agent 出错时，从用户看到的现象到根因，中间隔着好几跳：

```
答错了
 ├─ 知识库里根本没有这条      → 检索层（召回失败）
 ├─ 检索到了但没被用上         → 答案层（生成失败 / 上下文被截断）
 ├─ 该委派给子 Agent 却自己答   → 路由层（编排失败）
 └─ 都对了，是数据本身错了      → 数据层（库里的数不对）
```

不分层的话，一次失败的排查要同时怀疑四件事，而且**每次改动都无法证明"没变差"**。
所以把评测拆成三层，每层只回答一个问题：

| 层 | 回答的问题 | 依赖 | 跑一次的成本 |
|---|---|---|---|
| 检索层 | 该找到的片段，在 top-k 里吗？ | 只有 embedding | 秒级 |
| 答案层 | 用上检索结果后，回答覆盖了关键要点吗？ | embedding + LLM | 十几秒 |
| 路由层 | 该不该委派、委派给谁？ | 完整 Agent（沙箱 + MCP + PG） | 分钟级，且贵 |

外加一层**数据层自检**（`scripts/smoke_db.py`）：schema、种子数据、repository 的领域规则
（状态机、金额重算、非法输入）。这层不涉及 LLM，但最容易"看起来写了其实没跑"，
所以直接放进 CI 当回归。

## 2. 检索层：怎么判"找对了"

判定逻辑（`src/eval/run_eval.py`）：

1. 用 `knowledge_search` 取 top-k（默认 5）；
2. **来源命中**：`expected_sources` 里任意一个出现在 top-k 的 `source` 元数据中；
3. **相关度阈值**：top-1 的余弦分数不低于阈值，防止"来源碰巧落在列表末尾"也算通过。

为什么两个条件都要：只看分数会被 embedding 的分布漂移影响；只看来源又太宽松。
两者同时成立，才说明"检索确实指到了正确的文档"。

## 3. 答案层：怎么判"说对了"

把检索到的片段拼进 prompt 让模型回答，再检查 `expected_keywords` 是否覆盖。

关键约束：**锚点必须是原文里真实存在的字符串**（数字、标准号、专有名词），
不能是"模型应该会提到"的概括词。否则用例会随模型版本漂移，变成测模型而不是测系统。

反例（不要这么写）：

```yaml
expected_keywords: ["性价比高", "建议根据实际情况选择"]   # 无法机器判定，也无法复现
```

正例：

```yaml
expected_keywords: ["45 天", "预付 30%", "环氧树脂板"]     # 知识库原文里能直接 grep 到
```

## 4. 负例：最容易被忽略的一课

负例问的是知识库里**没有**的内容。正确答案不是"编一个合理的答案"，
而是**承认库里没有、并说明该怎么查**。

没有负例的评测集，会奖励"什么都敢答"的模型；有负例，才逼着系统在不确定时收敛。
这也是提示词里反复强调"所有结论基于真实数据、绝不编造"的配套措施。

## 5. 路由层：为什么现在是 skipped

路由层要判断"这句话该不该委派、该委派给哪个子 Agent"，必须跑完整 Agent：
沙箱创建 + MCP 工具加载 + PG checkpointer，一次几十秒到几分钟。

`run_eval.py` 目前**明确标注 skipped**，而不是假装通过：

```
[skip ] route-001: 路由层需完整 Agent 环境
```

约定：`passed=None` 表示 skipped —— 报告里的"通过率"不会把没跑的用例算成通过。
在线模式（`--with-agent`）是 TODO，写进了 README 的已知限制。

## 6. 用例设计的三条铁律

1. **一条用例只测一件事**。既测检索又测答案的用例，失败时无法定位。
2. **`expected` 只写可验证的事实**，不写开放式判断（"是否合理"没法自动化）。
3. **不要为了让模型通过而改 `expected`**。失败时该改的是知识库或提示词；
   改期望值等于把评测变成自证。

## 7. 怎么跑

```bash
python src/eval/run_eval.py                  # 检索层 + 答案层
python src/eval/run_eval.py --skip-answer    # 只测检索层（不调 LLM，最快）
python src/eval/run_eval.py --case rag-004   # 单条用例
```

- 报告写到 `src/eval/results/`（已在 `.gitignore`，属于本地产物）；
- 有失败时**退出码非零**，可以直接接 CI 当门禁。

## 8. 两类"正确性"不要混

| | 谁保证 | 怎么验 |
|---|---|---|
| 知识 / 回答是否正确 | 评测集（检索层 + 答案层） | `run_eval.py` |
| 业务数据是否正确 | 数据库约束 + repository 领域规则 | `scripts/smoke_db.py`（CI 里跑） |

举例：模型说"冷轧板 1.0mm 报价 165 元/张"——这句话对不对取决于库里那条报价，
属于第二类；模型有没有**正确地引用**库里那条报价，才是第一类要测的。
把两者混在一个评测里，分数掉了都不知道该改提示词还是改 SQL。
