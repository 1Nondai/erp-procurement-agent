# 第一部分 评测的思维方式

## 1.1 没有评测的世界

设想你接手了这个项目，老板说："把火花塞的知识换一版。"你改了 `knowledge_docs.py`，手动问了三个问题，看起来都对，发布了。

两周后用户投诉："现在问比价原则，它开始胡说八道了。"

发生了什么？你改的知识向量把"比价"相关问题的检索结果挤偏了——**改动有涟漪效应，而手动抽查永远只覆盖你想到的那几个问题**。

这就是没有评测的世界：

| 症状 | 根因 |
|---|---|
| 改一处，坏一处，发现晚一周 | 没有**回归**能力（改动后自动重验全量用例） |
| "感觉变好了" | 没有**量化**指标，凭印象决策 |
| 用户说答错了，团队吵"是知识没写好还是模型不行" | 没有**分层**定位能力 |
| 新人不敢动代码 | 没有**安全网** |

评测体系的本质：**把"这个系统好不好"从主观感受变成一组可重复执行的断言**。

## 1.2 分层评测：缩小故障定位半径

本项目的回答链路是三段接力：

```
用户问题 → [①路由] 委派给谁 → [②检索] 找到知识了吗 → [③生成] 答案对吗
```

如果只做端到端评测（问一句、看答案对不对），一条 FAIL 你不知道锅在谁：
- 路由错了，把分析题派给了订单子 Agent？
- 检索没命中，知识库里根本没有相关内容？
- 检索命中了，但生成时 LLM 没用上？

分层评测每层独立判定，故障定位半径从"整条链路"缩到"某一层"：

```
答案层 FAIL + 检索层 PASS  → 锅在生成（改提示词/换模型）
答案层 FAIL + 检索层 FAIL  → 锅在知识（改知识库内容或分段）
检索层 PASS + 路由 skip    → 离线链路正常，问题在 Agent 侧（路由/工具选择）
```

> **教学要点**：分层评测的思想直接来自软件测试金字塔（单元→集成→E2E）。单元测试便宜、定位准；E2E 贵、但验证真实体验。本项目对应：检索层（"单元"，只调 embedding API）→ 答案层（"集成"，embedding+LLM）→ 路由层（"E2E"，需要完整 Agent 环境，离线评测自动跳过）。

## 1.3 本项目评测体系全景

```
┌──────────────────────────────────────────────────┐
│  eval_cases.yaml（13 条用例：10正例+1负例+2路由） │
│    每条：query / expected / expected_sources/tags │
└──────────────────┬───────────────────────────────┘
                   │ load_cases()
                   ▼
┌──────────────────────────────────────────────────┐
│  run_eval.py（评测执行器）                        │
│                                                  │
│  for case in cases:                              │
│    ├─ tags 含 agent_routing → 记 skipped         │
│    ├─ 检索层：kb.search(query)                   │
│    │    期望来源 ∈ top-k 的 source 集合？        │
│    │    top1 分数 ≥ 0.35？                       │
│    └─ 答案层（tags 含 domain_answer）：          │
│         检索片段 + 问题 → LLM → 答案             │
│         答案包含 expected 关键词？               │
└──────────────────┬───────────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────────┐
│  输出                                            │
│    控制台：[PASS/FAIL/skip] 逐条 + 汇总通过率     │
│    JSON 报告：eval/results/eval_report_*.json    │
│    退出码：0 全过 / 1 有失败（可接 CI）           │
└──────────────────────────────────────────────────┘
```

# 第二部分 评测集设计：eval_cases.yaml

## 2.1 用例的数据结构逐字段讲解

一条完整用例（文件位于 `src/eval/eval_cases.yaml`）：

```yaml
- id: rag-002                        # ① 唯一标识
  query: "比价采购有什么原则？至少要几家报价？"   # ② 模拟用户输入
  expected: "三家"                    # ③ 期望答案必须包含的关键事实
  expected_sources: ["采购制度手册"]  # ④ 期望检索命中的知识来源
  tags: [rag_retrieval, domain_answer]  # ⑤ 决定跑哪几层
```

**每个字段的设计理由**：

| 字段 | 类型 | 作用 | 设计理由 |
|---|---|---|---|
| ① `id` | str | 定位用例 | 报告里 FAIL 时用 `--case rag-002` 单条复现；id 前缀分类（rag-/route-）便于统计 |
| ② `query` | str | 输入 | **必须写成真实用户口吻**，不是关键词（"比价原则"），因为 embedding 对口语化长句和干巴巴关键词的向量表现不同 |
| ③ `expected` | str | 答案层判定依据 | 只写**可验证的客观事实**（"三家""JASO""180"），绝不写"回答应该全面准确"这类无法机器判定的描述 |
| ④ `expected_sources` | list | 检索层判定依据 | 知识语料里每条都带 source 元数据（"采购制度手册"），检索结果会原样带回来源 → 判定变成集合包含检查 |
| ⑤ `tags` | list | 执行路由 | 脚本按 tags 决定这条用例跑哪几层——**评测行为写进数据，不写死在代码里**，加新评测层不用改执行器主体 |

> **教学要点**：`expected_sources` 能成立的前提是 `knowledge_docs.py` 里每条知识都标了 source。**评测集和知识库是配套设计的**——知识带元数据，评测才有判定锚点。这是"数据 schema 决定评测能力"的典型案例。

## 2.2 正例设计原则

以现有 10 条正例为样本，归纳出四条原则：

**原则①：覆盖面跟着知识库分区走**

看现有用例的 expected_sources 分布：

| 来源分区 | 用例数 | 覆盖内容 |
|---|---|---|
| 采购制度手册 | 3 | 订单状态机、比价原则、下单三要素 |
| 零部件知识库 | 4 | 火花塞热值、机油认证、轮胎规格、（刹车片/蓄电池在知识里暂无用例）|
| 库存管理规范 | 3 | 安全库存公式、呆滞处理、ABC 分类 |
| 供应商管理办法 | 1 | QSDC 四维 |

每个知识分区至少 1 条用例——**知识分区无覆盖 = 该分区坏了你不知道**。

**原则②：一问一锚点**

每条用例只锚定一个关键事实：

```yaml
# ✅ 好的设计：锚点唯一且客观
query: "供应商评估有哪几个维度？"
expected: "QSDC"

# ❌ 坏的设计：锚点模糊、无法机器判定
query: "供应商评估有哪几个维度？"
expected: "应该完整准确地说出质量、服务、交付、成本四个维度并解释权重"
```

第二条判不了——"完整""准确"没有可执行的判定语义。如果确实想验证多个事实，**拆成多条用例**。

**原则③：查询措辞多样化（同义改写）**

同一个知识点，用户有一万种问法。评测集应该收录**多种问法**测鲁棒性：

```yaml
- id: rag-001
  query: "采购订单有哪些状态，是怎么流转的？"     # 列举式问法
- id: rag-009
  query: "呆滞物料怎么处理？库龄多久算呆滞？"     # 处置式问法
```

将来扩充方向（见第五部分实验）：给同一 expected 加"口语版""错别字版""混合多主题版"问法。

**原则④：边界数值型事实优先**

"180 天""三家""120/70-ZR17"这类**数字/代码型事实**是最好的锚点——模型答对了必然包含精确字符串，答错了必然对不上。比形容词类锚点可靠一个数量级。

## 2.3 负例设计——最容易被忽略的一课

```yaml
- id: rag-neg-001
  query: "公司食堂本周菜单是什么？"
  expected: ""
  expected_sources: []        # 空 = 负例
  tags: [rag_retrieval]
  note: "负例：知识库无此内容，top1 相关度应显著低于正例"
```

**为什么需要负例**：只有正例的评测集验证的是"查得到的能不能查准"；负例验证的是"**查不到的是不是知道自己查不到**"。

这是 RAG 幻觉问题的第一道防线。如果知识库里没有食堂菜单，理想的系统行为是"知识库中暂无相关内容"（`knowledge_search` 工具的空结果分支）；糟糕的行为是把向量空间里"最近"的某条库存知识硬扯过来一本正经地胡说——**检索系统天生倾向于返回点什么，负例就是在测试它的克制**。

**当前实现诚实说明**：`eval_retrieval()` 对负例目前只做链路级检查（`passed = isinstance(results, list)`），相关度阈值判定未启用——注释里写明"留人工/后续升级为 LLM judge"。这是**有意的教学留白**：第六部分的扩展实验就是让你把负例判定做实（例如断言 top1_score < 某个低阈值）。

## 2.4 路由用例设计

```yaml
- id: route-001
  query: "帮我分析一下火花塞供应商的价格对比"
  expected: "procurement-analyst"       # 期望被委派的子 Agent 名
  expected_sources: []
  tags: [agent_routing]
  note: "应委派给采购分析子 Agent"

- id: route-002
  query: "创建一个采购订单，物料 12 个火花塞"
  expected: "procurement-order"
  tags: [agent_routing]
  note: "应委派给采购订单子 Agent，且触发 HITL 审批"
```

设计逻辑：路由正确性 = **主 Agent 的 `task` 工具调用参数里子 Agent 名是否正确**。判定锚点直接用子 Agent 名（"procurement-analyst"），客观精确。

两条用例刻意选了"容易混淆的对照组合"——都涉及火花塞、都像业务操作，但一个要分析（analyst）一个要下单（order）。**路由评测的用例价值集中在"边界模糊的任务对"上**：两个都明确该找谁的任务，测不出路由质量。

## 2.5 维护约定：三条铁律

写在 `eval_cases.yaml` 文件头注释里，课堂应逐条解释：

```yaml
# 维护约定：
#   1. 每条 expected 只写"可验证的关键事实"，不写开放式内容；
#   2. 新增知识后同步补充对应用例（保证评测集覆盖率跟上知识库）；
#   3. 不要为了"让模型通过"修改 expected——修的是知识或提示词。
```

**铁律③是灵魂**，它防的是评测体系最经典的腐化路径：

```
模型答错 → 有人把 expected 改宽（"三家"→"三"）→ 通过率上升
        → 换个人再改宽（"三"→"几"）→ 评测变成橡皮图章
```

**expected 是标准，标准只能因为"需求本身变了"而改，不能因为"实现达不到"而改**。实现达不到时，要么修实现，要么承认这是个已知 FAIL（登记 issue）。

# 第三部分 评测脚本代码精讲：run_eval.py

## 3.1 文件骨架与全局常量

```python
# 保证可以从 src 目录导入 rag / agent 包
_SRC = Path(__file__).resolve().parent.parent
sys.path.insert(0, str(_SRC))

from rag.knowledge_base import KnowledgeBase

_SCORE_THRESHOLD = 0.35      # 相关度阈值：低于该分数的命中视为"弱相关"
_ANSWER_MODEL_NAME = "deepseek-chat"   # 答案生成模型
```

**两个常量的角色**：

- `_SCORE_THRESHOLD = 0.35`：检索层的第二道判据。光"来源命中"不够——如果命中的那条知识 top1 分数只有 0.2，说明语义相关性很弱，可能是"碰巧"命中的。0.35 的来历见 [4.2 节](#42-阈值-035-是怎么定的)。
- `_ANSWER_MODEL_NAME`：注意评测用的生成模型与被测系统**不是同一个配置**（被测系统用 deepseek-v4-pro/deepseek-chat 由 config.py 管理）。评测模型是评测基础设施的一部分——这个解耦意味着将来被测系统换模型，评测口径保持稳定。

**导入设计细节**：`sys.path.insert` 让脚本可以从任何工作目录直接 `python src/eval/run_eval.py` 运行，不依赖 PYTHONPATH 环境变量——**降低使用者门槛**是评测工具可用性的重要部分（用不了的评测等于不存在）。

## 3.2 load_cases()：加载用例

```python
def load_cases(path: Path) -> list[dict]:
    """加载评测用例 YAML。"""
    data = yaml.safe_load(path.read_text(encoding="utf-8"))
    return data.get("cases", [])
```

12 行说明加 2 行代码——**最简单的函数反而值得讲两件事**：

1. `yaml.safe_load`（不是 `load`）：评测集是数据文件，永远不该被解析成任意 Python 对象（YAML 反序列化攻击面）。用 `safe_load` 是纪律。
2. 返回 `data.get("cases", [])` 而不是 `data["cases"]`：YAML 整个文件为空时返回 `None`，`.get` 兜成空列表——评测脚本对**用例文件的空态**也要健壮。

## 3.3 eval_retrieval()：检索层判定逻辑

这是检索层的核心函数，逐段精讲：

```python
async def eval_retrieval(kb: KnowledgeBase, case: dict, top_k: int) -> dict:
    """评测单条用例的检索质量。

    判定规则：
        - 正例（expected_sources 非空）：每个期望来源都必须在 top-k 的
          source 集合中出现，且 top1 分数不低于阈值；
        - 负例（expected_sources 为空）：只检查"检索不崩溃 + 返回条数正确"，
          相关度阈值不做硬判定。
    """
    await kb.ensure_built()                          # ① 幂等构建知识库
    results = await kb.search(case["query"], top_k=top_k)   # ② 真实检索
    got_sources = [r["meta"].get("source", "") for r in results]  # ③ 提取来源
    top1_score = results[0]["score"] if results else 0.0         # ④ top1 分数
```

**执行链路**：这里调用的是**被测系统的真实代码路径**（`KnowledgeBase.search`），不是评测自己重新实现一份检索——**评测必须测真实链路**，重新实现的"参考实现"会掩盖被测代码的 bug。

**正例判定（三条件与逻辑）**：

```python
    expected_sources = case.get("expected_sources") or []
    if expected_sources:
        missing = [s for s in expected_sources if s not in got_sources]
        passed = (not missing) and top1_score >= _SCORE_THRESHOLD
```

拆开看，一条正例要 PASS 必须同时满足：

| 条件 | 代码 | 防什么 |
|---|---|---|
| 所有期望来源都命中 | `not missing` | 期望两个来源只命中一个 → 半对也是错 |
| top1 分数达标 | `top1_score >= 0.35` | 碰巧命中：向量空间里最近的恰好是它，但语义相关性弱 |

**注意判定粒度是"来源"而不是"片段原文"**：知识库某分区可能有多条片段（"采购制度手册"下有 4 条）。判来源不判原文，是因为知识内容会被编辑润色（片段文本变），但来源分区稳定——**锚点选稳定的那一层**，否则每次改知识措辞都要同步改一批用例。

**负例判定（宽松模式）**：

```python
    else:
        # 负例：只验证检索链路正常工作
        passed = isinstance(results, list)
        detail = {"top1_score": round(top1_score, 4), "negative_case": True}
```

返回值记录仍带 `top1_score`——虽然不判定，**但数据留在报告里**。这是评测工具的通用习惯：无法自动判定的信息原样落盘，供人工抽查或后续升级判定逻辑时有据可查。

**返回结构（三层评测统一契约）**：

```python
    return {
        "case_id": case["id"],
        "layer": "retrieval",
        "passed": passed,
        "detail": detail,          # 判定证据全在这，FAIL 时看它定位
    }
```

`detail` 里放判定证据（期望什么/得到什么/差在哪）——**报告的可读性设计：FAIL 的人不需要重跑就能知道为什么 FAIL**。

## 3.4 eval_answer()：答案层判定逻辑

```python
async def eval_answer(kb: KnowledgeBase, case: dict, top_k: int, llm) -> dict:
    """评测"检索 + 生成"端到端：RAG 上下文下答案是否含期望要点。

    之所以要求"必须包含 expected 关键词"而不是自由打分：
        评测集里的 expected 都是客观事实（如"三家""JASO"），
        包含性检查可复现、无 LLM judge 的随机性。
    """
```

**函数内五个步骤**：

```python
    # ① 无 LLM Key → 记 skipped（None），不是 FAIL
    if llm is None:
        return {"case_id": ..., "layer": "answer", "passed": None,
                "detail": {"reason": "DEEPSEEK_API_KEY 未配置，答案层跳过"}}

    # ② 复用同一次检索结果组织上下文
    results = await kb.search(case["query"], top_k=top_k)
    context = "\n\n".join(
        f"[{i}] ({r['meta'].get('source', '')})\n{r['text']}"
        for i, r in enumerate(results, 1)
    )

    # ③ 受控 prompt：这是"评测脚手架"自己的提示词
    prompt = (
        "你是 ERP 采购助手。请仅根据以下知识库片段回答问题，"
        "不要编造片段之外的内容。\n\n"
        f"知识库片段：\n{context}\n\n问题：{case['query']}\n\n"
        "请用两三句话回答。"
    )

    # ④ 生成
    resp = await llm.ainvoke(prompt)
    answer = resp.content if isinstance(resp.content, str) else str(resp.content)

    # ⑤ 关键词包含判定
    expected = (case.get("expected") or "").strip()
    passed = (not expected) or (expected in answer)
```

**步骤③的深意（教学重点）**：这条 prompt 是评测脚手架的，**不是**被测 Agent 的真实系统提示词。答案层测的是"给定正确的检索上下文，一个标准配置的 LLM 能不能组织出含关键事实的回答"——它剥离了主 Agent 的路由、委派、子 Agent 提示词等所有变量，**单独归因于"检索质量 + 基础生成能力"**。这就是分层评测里"集成测试"的边界划定：集成层测管线，不测被路由包裹的完整系统。

**步骤⑤的两个细节**：
- `expected.strip()`：用例 YAML 里的字符串可能带尾随空白，先规范化——**判定代码要原谅数据的小瑕疵，但对判定本身要严格**；
- `(not expected) or (expected in answer)`：expected 为空的用例（负例、纯路由用例）不进答案层判定逻辑，这里做防御性兜底。

**答案截断进报告**：`"answer": answer[:300]`——报告是给人看的，300 字足够定位"关键事实说了没"；完整答案会撑大报告文件（13 条 × 每条若干百字，重复信息居多）。

## 3.5 main()：主流程与命令行参数

主流程按执行顺序拆成六段：

**第①段：命令行接口**

```python
parser.add_argument("--top-k", type=int, default=5)      # 检索条数
parser.add_argument("--case", type=str, default=None)   # 只跑指定用例
parser.add_argument("--skip-answer", action="store_true")  # 跳过答案层
```

三个参数对应三类使用场景：

| 参数 | 场景 |
|---|---|
| `--case rag-004` | 一条 FAIL 后的单条复现（调试循环的核心） |
| `--skip-answer` | 只测检索层——不调 LLM，**零成本、最快速度**，适合改知识库后的快速回归 |
| `--top-k 3` | 调研检索参数敏感性（top_k 调小后命中率变化） |

**第②段：用例筛选**

```python
cases = load_cases(Path(__file__).parent / "eval_cases.yaml")
if args.case:
    cases = [c for c in cases if c["id"] == args.case]
    if not cases:
        print(f"找不到用例: {args.case}")
        return 2
```

注意返回码 2（用法错误）——与"评测失败"的 1 区分开，CI 里能分辨"脚本用错了"和"系统变差了"。

**第③段：前置 Key 检查（fail-loud 教学范本）**

```python
from agent.env_utils import ZHIPU_API_KEY
if not ZHIPU_API_KEY:
    print(
        "错误：ZHIPU_API_KEY 未配置，检索层评测无法运行（embedding 不可用）。\n"
        "请在项目根目录 .env 中添加：\n"
        "    ZHIPU_API_KEY=你的智谱API密钥\n"
        "配置后重新运行本脚本。"
    )
    return 2
```

对比反面设计：不做前置检查 → 用户跑起来 → 第一条用例深处抛 `ValueError: ZHIPU_API_KEY 未配置` 的 traceback → 用户在堆栈里找原因。**错误信息要在离根因最近的地方报，且报出来的就是修复指引**。这个模式值得在所有工具类脚本里复用。

**第④段：按 tags 路由执行**

```python
for case in cases:
    tags = case.get("tags", [])

    # 路由层用例需要完整 Agent 环境，离线跳过
    if "agent_routing" in tags:
        rec.update(layer="routing", passed=None,
                   detail={"reason": "路由层需完整 Agent 环境，离线评测跳过"})
        records.append(rec)
        continue

    # 1) 检索层（所有用例都跑）
    r = await eval_retrieval(kb, case, args.top_k)
    records.append(r)

    # 2) 答案层（只有 tags 含 domain_answer 且未 skip 时跑）
    if "domain_answer" in tags and not args.skip_answer:
        r2 = await eval_answer(kb, case, args.top_k, llm)
        records.append(r2)
```

**用例到执行记录是 1:N 关系**：一条用例可能产生多条记录（检索层一条 + 答案层一条）。汇总统计时按 `layer` 字段过滤——这就是为什么每条记录都带 `layer` 标签。

**第⑤段：计时**

```python
t0 = time.time()
r = await eval_retrieval(...)
print(f"[{mark}] {case['id']} 检索层 ({time.time()-t0:.1f}s) top1={...}")
```

逐条耗时打印——评测工具自身的性能也是观测对象（embedding API 慢、网络抖动，从这里的耗时会先看出来）。

**第⑥段：汇总与落盘**（见下一节）

## 3.6 报告格式与退出码设计

**汇总输出**：

```python
retrieval_recs = [x for x in records if x["layer"] == "retrieval"]
answer_recs = [x for x in records if x["layer"] == "answer" and x["passed"] is not None]
print(f"检索层: {sum(1 for x in retrieval_recs if x['passed'])}/{len(retrieval_recs)} 通过")
```

注意 `answer_recs` 的过滤条件里 `x["passed"] is not None`——**skipped 的记录不进分母**。分母里混入 skipped 会虚低通过率，误导 CI 判定。

**落盘报告**：

```python
out_dir = Path(__file__).parent / "results"
report_path = out_dir / f"eval_report_{datetime.now().strftime('%Y%m%d_%H%M%S')}.json"
report_path.write_text(
    json.dumps({"records": records}, ensure_ascii=False, indent=2, default=str),
    encoding="utf-8",
)
```

设计细节：
- 文件名带时间戳：每次运行都是新文件 → **天然形成历史序列**，可以对比"上周 90% → 本周 76%"；
- `ensure_ascii=False`：中文答案原样写入，报告可直接阅读；
- `default=str`：detail 里有非 JSON 原生类型时降级为字符串，**报告写入永不因数据类型崩溃**；
- 目录 `src/eval/results/` 已在 `.gitignore` 里——本地产物不进版本库。

**退出码约定（接 CI 的关键）**：

```python
failed = any(x["passed"] is False for x in records)
return 1 if failed else 0
```

| 退出码 | 含义 | CI 行为 |
|---|---|---|
| 0 | 全部通过（skipped 不算失败） | 绿灯 |
| 1 | 存在 FAIL | 红灯，阻断合并 |
| 2 | 用法错误 / 环境没配好 | 红灯，但报"配置问题"而非"质量回退" |

```yaml

  run: python src/eval/run_eval.py --skip-answer
  env:
    ZHIPU_API_KEY: ${{ secrets.ZHIPU_API_KEY }}
```

# 第四部分 判定方法论的深入讨论

## 4.1 为什么用"关键词包含"而不是 LLM 打分

这是本评测体系最重要的一个设计决策，值得用整节课讨论。

当前方案（关键词包含）：

```python
passed = expected in answer      # "三家" in "……至少取得三家有效报价……"
```

替代方案（LLM-as-judge，用另一个模型给答案打分）：

```python
# 伪代码
score = await judge_llm(f"问题：{q}\n参考答案：{expected}\n学生答案：{answer}\n评分1-5")
passed = score >= 4
```

**对比分析**：

| 维度 | 关键词包含 | LLM-as-judge |
|---|---|---|
| 可复现性 | 100%（同一输入永远同一结果） | 同一答案跑两次可能一个 4 分一个 3 分 |
| 成本 | 零额外调用 | 每条用例多一次 LLM 调用 |
| 可判定范围 | 只能判"事实是否出现" | 能判"全面性/逻辑性/语气" |
| 被操纵风险 | 低 | 高（答案讨好 judge 的措辞就能提分） |
| 实现复杂度 | 1 行 | prompt 工程 + 分数解析 + 稳定性处理 |

**本项目的取舍逻辑**：评测集里的 expected 全部是**客观事实**（数字、认证名、维度缩写），这类问题的正确判定关键词包含完全胜任；而**可复现性**对回归测试是刚需——回归测试的价值就在于"今天 FAIL 的就是昨天 PASS 的那条改动弄坏的"，judge 的随机性会淹没这个信号。

**方法论结论（板书级总结）**：
> **回归评测用确定性判定（关键词/规则/精确匹配），主观质量评测用 LLM-as-judge，两者不要混用一套体系。** 本项目把 LLM-as-judge 列为扩展方向（第六部分），而不是基础能力，就是这个原因。

## 4.2 阈值 0.35 是怎么定的

`_SCORE_THRESHOLD = 0.35` 不是从教科书抄的，是**经验标定值**。讲清楚它的来历，学生才能理解"阈值应该怎么定"：

**第一步：理解分数的物理含义**

余弦相似度范围 [-1, 1]（embedding 实际输出通常落在 [0, 1] 区间）：

| 分数段 | 语义 |
|---|---|
| > 0.7 | 强相关（同一知识点的同义问法） |
| 0.35 ~ 0.7 | 中等相关（同领域，话题相邻） |
| < 0.35 | 弱相关/不相关（向量空间里只是"最近"而已） |

**第二步：在真实数据上标定**

拿本评测集跑一遍，看正例的 top1 分数分布。如果正例普遍在 0.5+ 而跨领域误命中在 0.2~0.3，那么 0.35 就是分水岭——**阈值应该落在"正例分布下界"和"误命中分布上界"之间**，两边都留余量。

**第三步：明白它的局限**

阈值不是一劳永逸的：换 embedding 模型（分数分布整体位移）、知识库结构变化后，都要重新标定。**所以它写成模块级常量而不是硬编码在判定表达式里**——集中一处，改起来有据可查（更好的做法是环境变量可配，留作扩展）。

> **课堂金句**：阈值是标定出来的，不是拍脑袋出来的；且换模型必须重标。

## 4.3 skipped 不是 failed：三态判定

本脚本 `passed` 字段有三态，这是很多评测系统做错的地方：

```python
passed: True    # 判定了，通过
passed: False   # 判定了，失败        → 退出码 1
passed: None    # 没判定（环境不具备） → 退出码 0，日志标注 [skip]
```

skipped 的两个来源：

| 来源 | 触发条件 | 正确处理 |
|---|---|---|
| 路由层用例 | tags 含 agent_routing，但离线运行 | 记录 reason，不进通过率分母 |
| 答案层 | DEEPSEEK_API_KEY 未配置 | 同上 |

**为什么必须区分**：想象 CI 里 13 条用例 8 条 FAIL——如果 skipped 也算 FAIL，你无法区分"系统真的回退了"和"CI 机器没配 Key"。**把"测不了"混进"没通过"，评测体系自己就成了噪音源**。

反面案例（真实世界）：某 CI 的测试套件长期 30 个用例"红着"，因为里面 28 个需要内网数据库连不上——大家对红灯麻木了，剩下 2 个真 FAIL 从来没人看。**这就是 skipped 与 failed 不分的代价**。

## 4.4 Goodhart 定律：当评测成为目标

> **Goodhart's Law**：当一个度量变成目标，它就不再是一个好的度量。

放到本项目的语境里推演三种腐化场景：

**场景①：直接改 expected**（2.5 节铁律③防的）
```
FAIL → 把 expected 从 "三家" 改成 "报价" → PASS
     → 评测通过率 100%，系统质量没变甚至更差
```

**场景②：知识库为评测而写**（更隐蔽）
```
用例问"至少要几家报价"
→ 有人往知识里机械地写"至少要三家报价"
→ 知识可读性下降、上下文价值稀释（对真实用户没用的复读）
```
防御方法：知识编辑和用例编写**不是同一个人/同一时刻**做（知识先行，用例事后对照业务事实写）。

**场景③：prompt 过拟合评测集**
```
反复调提示词直到 13 条全 PASS → 提示词记住的是这 13 个问题
→ 第 14 个真实用户问题表现未知
```
防御方法：**保留一部分用例不参与调优**（holdout，训练/测试集分离思想）——平时跑 10 条，发布前跑全量含 holdout 的 13 条。

**课堂结论**：评测是通过率的**裁判**，不是通过率的**垫脚石**。所有让"分数好看"而不是让"系统变好"的动作，都在拆评测的墙角。

# 第五部分 教学实践设计

## 5.1 五个课堂实验

由浅入深，每个实验都产出可检查的交付物：

### 实验 1：跑通与读懂报告（30 分钟）
- 配好 ZHIPU_API_KEY 后运行 `python src/eval/run_eval.py`；
- 打开 `src/eval/results/` 里最新的 JSON 报告，逐字段讲解 records 里的一条 FAIL 记录（detail 里的证据链）；
- 再跑 `--skip-answer` 和 `--case rag-004`，对比三次输出的差异；
- **交付**：写一段"检索层和答案层各测了什么、skipped 意味着什么"。

### 实验 2：扩充评测集（45 分钟）
- 在 `knowledge_docs.py` 里加一条新知识（如"刹车片摩擦系数国标 0.25-0.55"）；
- 按 2.2 节四原则**独立设计** 2 条正例（一个数字锚点 + 一个非数字锚点）+ 1 条负例；
- 跑评测验证新用例 PASS；
- **交付**：新用例 YAML + 一段设计说明（为什么选这个锚点）。
- **检查点**：锚点是不是客观事实？负例是不是真的"知识库里没有"？

### 实验 3：负例判定做实（60 分钟，代码实验）
- 现状：负例只检查链路不崩。任务：给 `eval_retrieval()` 增加负例的 top1_score 上限断言（如 `top1_score < 0.45`，阈值自己标定：先跑全部正例取分数下界作参考）；
- 跑通后故意往知识库加一条食堂菜单知识，验证负例会"变红"（因为现在查食堂真的能查到东西了）；
- **交付**：代码 diff + 标定过程记录（正例分数分布 → 阈值选择理由）。
- **教学意图**：体验"阈值标定"完整流程。

### 实验 4：LLM-as-judge 对比实验（45 分钟，方法论实验）
- 给答案层加一个 `--judge` 模式：用另一个 LLM 按 1-5 分打分（≥4 判过）；
- 对同一批答案分别用关键词包含和 judge 判定，统计**两法结论不一致的用例**；
- 对不一致的用例，把 judge 连跑 3 次看分数抖动；
- **交付**：不一致清单 + 抖动观察 + 一段结论（"什么类型的问题 judge 更不可靠"）。
- **教学意图**：亲手复现 4.1 节的对比分析，胜过十页论述。

### 实验 5：接入 CI（30 分钟）
- 写一个 GitHub Actions workflow（或本地 pre-commit hook）：push 时自动跑 `run_eval.py --skip-answer`；
- 故意改坏一条知识（把"三家"改成"两家"），push 后观察 CI 红灯定位到对应用例；
- **交付**：workflow 文件 + 红灯截图。
- **教学意图**：完成"评测 → 回归防线"的最后一块拼图。

## 5.2 课堂讨论题

1. **（分层思维）** 用户反馈"答错了"，在只有端到端评测的团队里排障流程 vs 有三层评测的团队里排障流程，差在哪？（答：定位半径——前者逐段手动复查，后者看 FAIL 落在哪层直接进对应代码）
2. **（锚点选择）** "expected: 摩托车机油需要看 JASO 认证" 和 "expected: JASO" 作为判定锚点有什么区别？（答：前者要求答案包含整句原话，误杀合法改写；后者是唯一事实核，任何正确表述都包含它）
3. **（三态判定）** 如果 CI 机器永远配不上 LLM Key，答案层永远 skipped——这算评测体系缺陷吗？（答：不算缺陷算降级，但要在报告里可见；长期 0 覆盖的层应该有"最低限度人工抽测"补位）
4. **（Goodhart）** 老板要求"评测通过率下周提到 100%"，作为评测负责人你该怎么回应？（答：通过率是度量不是目标；先区分 FAIL 清单里"实现该修的"和"评测本身有问题的"，各自建账，绝不动 expected 凑数）
5. **（扩展推理）** 如果知识库从 14 条涨到 14000 条，本评测体系哪里先扛不住？（答：负例语义漂移——大规模知识库下"食堂菜单"可能真的有相近条目；以及评测集覆盖率的维护成本——需要按分区自动统计覆盖率）

# 附录 B 评测领域术语表

| 术语 | 一句话解释 |
|---|---|
| **评测集（eval set）** | 结构化的"输入-期望"对集合，机器可执行的质量断言 |
| **回归测试** | 改动后重跑既有用例，确认没弄坏原本正常的能力 |
| **分层评测** | 按系统链路分段独立判定，缩小故障定位半径 |
| **判定锚点（anchor）** | 用例里用于机器判定的客观事实（关键词/来源/ID） |
| **正例 / 负例** | 期望系统"做到"的用例 / 期望系统"承认做不到"的用例 |
| **LLM-as-judge** | 用另一个 LLM 给开放式答案打分的判定方法，有随机性 |
| **holdout** | 不参与日常调优、只在关键节点启用的保留用例，防过拟合 |
| **三态判定** | passed = True / False / None(skipped)，测不了≠没通过 |
| **Goodhart 定律** | 度量变成目标后就失去度量价值 |
| **top-k** | 检索返回的相关性最高的 k 条结果 |
| **top1 分数** | 最相关一条的相关度，检索质量的单值摘要 |
| **余弦相似度** | 向量夹角余弦，RAG 检索的标准相关性度量 |
| **退出码（exit code）** | 脚本结束状态码，CI 据此判红绿灯（0 过/1 败/2 用法错） |
| **fail-loud** | 环境不满足时立刻、明确地报错并给出修复指引 |
